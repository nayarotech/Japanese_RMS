# 16. Menu item photos

Implemented: one primary photo per menu item, uploaded by owners and managers, shown everywhere the menu is shown
(restaurant admin, POS, table QR menu, online ordering). Out of scope: galleries, video, a media library, CDN management.

## Data flow

```
Admin editor ──PUT raw bytes──▶ API: authorize ▶ read ≤5 MB ▶ sniff + decode + re-encode (Sharp) ▶ object storage
                                                                         │
                                              PostgreSQL menu_item_images (metadata only, RLS)
                                                                         │
getMenu() ──▶ admin /menu, POS /menu, QR /public/tables/:token, online /public/stores/:token  (URLs + dimensions)
Browser <img> ──▶ STORAGE_PUBLIC_BASE_URL/<key>  (CDN / public bucket)   or   /api/v1/public/media/<key> (API route)
```

All four interfaces read the photo through the single `getMenu` read model (`apps/api/src/modules/menus/index.ts`) and
render it with one component (`apps/web/src/components/MenuItemImage.tsx`). There is one upload implementation.

## API

| Method and path                       | Who                                   | Body / result                                                                                                  |
| ------------------------------------- | ------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `PUT /api/v1/menu/items/:id/image`    | `menu.manage` (owner, manager) + CSRF | Raw file bytes, `Content-Type: image/jpeg, image/png or image/webp`. `201` added / `200` replaced, `{ image }` |
| `DELETE /api/v1/menu/items/:id/image` | `menu.manage` + CSRF                  | `204` (idempotent). The item shows its placeholder.                                                            |
| `GET /api/v1/public/media/<key>`      | anyone (rate limited per IP)          | The WebP rendition, `Cache-Control: public, max-age=31536000, immutable`. Active photos only.                  |

Menu responses carry `image: { url, thumbUrl, width, height, thumbWidth, thumbHeight } | null` (contracts: `MenuImageDto`).
No binaries, keys of other tenants, bucket names or credentials are ever returned. Lists, POS tiles and QR/online menus
load `thumbUrl` only; `url` (up to 1200 px) is used for the large preview in the editor.

Error codes (localized in the web app): `unsupported_image_type` 415, `image_too_large` 413, `invalid_image` 422,
`image_dimensions_invalid` 422, `image_missing` 400, `storage_unavailable` 503, `image_processing_busy` 503,
`rate_limited` 429, `forbidden` 403, `not_found` 404 (unknown item or another restaurant's item).

## Validation and processing (`modules/menus/images/processing.ts`)

1. Size: body limit `MENU_IMAGE_MAX_BYTES` (5 MB) enforced while reading; the proxy allows 6 MB on this route only.
2. Type: identified from the **file signature** (JPEG `FF D8 FF`, PNG signature, `RIFF....WEBP`). The declared MIME type
   only gates the body parser; file names are never sent. SVG, GIF, HEIC, TIFF, PDF and everything else are refused
   before any decoder runs, so no other libvips loader is reachable from user input.
3. Header check: the decoder's format must match the signature; width/height must be 32–10,000 px and at most 40 MP
   (decompression bombs are refused from the header, and `limitInputPixels` enforces it again during decoding).
4. Decode strictly (`failOn: "warning"`: truncated or corrupt files are rejected), first frame only.
5. Re-encode: EXIF orientation applied, converted to sRGB, **all metadata stripped** (EXIF, GPS, XMP, ICC), resized
   with `fit: inside` (aspect ratio kept, never enlarged) to **main ≤ 1200 px** (WebP q82) and **thumbnail ≤ 320 px**
   (WebP q76). The original upload is never stored or served.
6. At most 2 photos are processed at once per API process (8 more may wait, then 503), so uploads cannot starve
   ordering and checkout of CPU or memory. Uploads are limited to 30 per staff session per 10 minutes.

## Storage (`infrastructure/storage/object-storage.ts`)

`ObjectStorage` interface (`put`, `get`, `delete`, `publicUrl`) with three drivers selected by `STORAGE_DRIVER`:
`s3` (any S3-compatible service; **required in staging/production**, enforced at startup), `local` (a directory, for
single-host development) and `memory` (tests, with fault injection). Keys are generated by the server only:
`menu-images/<tenant id>/<128-bit random>/{main,thumb}.webp`; every driver rejects any other key shape, and the local
driver additionally refuses paths outside its root. A CHECK constraint ties each key to its row's tenant prefix.

Delivery: if `STORAGE_PUBLIC_BASE_URL` is set (CDN or public-read bucket), URLs point there. Otherwise the API's media
route serves the object after confirming, under that tenant's RLS context, that the key is an **active** photo. Forged
keys, another tenant's prefix and replaced/removed photos return 404. Objects are immutable (a new photo always gets a
new key), so browsers and CDNs can cache them for a year without invalidation.

## Data model (`migrations/2026112401_menu_item_images.ts`)

`app.menu_item_images` (RLS `tenant_isolation`, runtime role cannot DELETE): tenant, location, menu item, status,
storage keys, content type, main and thumbnail width/height/bytes, source type and bytes, uploader, timestamps,
cleanup attempts. A partial unique index allows **one `active` photo per item**. `menu_items` is unchanged; items
without a row simply have no photo. The migration is additive and has a `down` (drops the table).

### Lifecycle: replacement and deletion without losing a photo

| Status    | Meaning                                                                                |
| --------- | -------------------------------------------------------------------------------------- |
| `pending` | Row written, objects being uploaded. Invisible. A crash here leaves a row we can find. |
| `active`  | The item's photo.                                                                      |
| `retired` | Replaced, removed or failed. Objects are due for deletion. Never reactivated.          |
| `deleted` | Objects deleted. Tombstone kept for the audit trail.                                   |

Replace = process in memory → insert `pending` → upload both renditions → in one transaction lock the item row, retire
the current photo, activate the new one, write the audit event → **after commit** delete the old objects. No
transaction is held open during storage I/O. Failures:

- Upload fails: the half-written objects are deleted and the row retired; the existing photo is untouched (503).
- Activation fails: the new objects are deleted; the existing photo is untouched.
- Deleting old objects fails: the replacement still succeeds; the row stays `retired` and is retried.
- Process crashes mid-upload: `pending` rows older than 15 minutes are claimed atomically (an activation and a claim
  cannot both win) and their objects deleted.

The sweep (`purgeRetiredImages`) runs for the tenant after every photo change. Audit actions:
`menu.item.image_added`, `menu.item.image_replaced`, `menu.item.image_removed`.

## Web

- `MenuPhotoField` (Add/Edit item dialog): click or drag-and-drop, instant local preview (object URL), replace,
  remove with undo until saved, client-side size/type checks (signature sniffing, same rules as the server), upload
  progress (XHR), localized errors. The photo is uploaded after the item is saved; if only the photo fails, the item
  stays saved and the dialog stays open on it to retry.
- `MenuItemImage`: thumbnail, `loading="lazy"`, `decoding="async"`, explicit width/height, `object-cover` in a fixed
  box (no distortion), `alt` = the item's localized name, and the existing brand-tinted initial as the placeholder (also
  used if the image fails to load).

## Production setup still required

1. Create a private bucket; grant the API role `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject` on `menu-images/*`
   only (prefer a task role over static keys). Enable default encryption and block public ACLs.
2. Either put a CDN in front of the bucket (origin access restricted to the CDN) and set `STORAGE_PUBLIC_BASE_URL`,
   or leave it empty and let the load balancer route `/api/v1/public/media/*` to the API (cache it at the CDN/LB).
3. Raise the load balancer / WAF body limit to 6 MB for `PUT /api/v1/menu/items/*/image` only (see `infra/proxy/nginx.conf`).
4. Schedule a periodic cross-tenant sweep of `retired` and stale `pending` rows (the in-request sweep only covers
   tenants that change photos). This needs a durable job runner (ADR-0004, not chosen yet) or an operator task.

Do not use an age-based bucket lifecycle rule as a backstop: active photos are old too. Rely on the sweep.
